# McTrail · 麦路同行

Run. Ride. Refuel.

先规划用户想跑、想骑的路线，再安排沿途麦当劳休息与补给点。
这是出行前规划，不是实时导航、专业运动指导或夜间安全认证。
第一版只读，不创建订单、领券、兑换、抽奖或读取账户地址和历史订单。

## 1. 确认本次出行

一次补齐缺失的必要信息，已有信息不重复问：

- 城市、明确起点；点到点还需终点。不要用 IP、账户地址或聊天以外的资料猜位置。
- 跑步 / 骑行，环线 / 点到点。
- 出发日期、时间、时区；中国大陆出行使用北京时间，输出注明跨日日期。
- 环线的目标里程或时长；用户有硬性上限时原样保留。
- 跑步配速；未知时先问，不把地图步行耗时当跑步耗时。
- 是否需要途中补给、终点补给，每站停多久；不要默认每经过一家店都停。

时长目标需要说明是否包含休息。夜间模式遵循用户的出发计划，不靠当前时刻自动猜。
用户只要求普通点餐、查询优惠券时，不启用本 Skill。

## 2. 检查数据与工具

先读 [工具与证据约定](references/tools.md)，发现当前宿主实际提供的工具与参数。
地图使用地理编码、步行/骑行路径、POI；麦当劳使用时间与附近门店查询。
工具名称可能有服务器前缀，不把参考名称当成一定存在的接口。

需要路网和门店两类真实数据。缺少连接时明确说缺哪个，并给配置指引；
只有用户明确接受时才输出“仅地图路线，麦当劳补给未验证”。
离线示例只用于演示计算，不能成为真实出行推荐。

只把完成查询必需的位置发给相应服务。不读取 Token 文件，不把凭据放进提示词、
命令、路线卡片、日志或仓库；MCP 鉴权由宿主配置负责。

## 3. 先确定点位，再查询路线

每个起点、终点、途经点和补给点，都先按
[地点解析规则](references/place-resolution.md) 完成一次定位，再调用步行/骑行路由。
没有通过定位的点，不能用于路由、路线计算或地图入口生成；不要先算一圈再检查起点。

| 用户提供的位置 | 下一步 |
|---|---|
| 广场、公园、建筑、景点、车站等名称 | `maps_text_search` 按城市搜索，筛选语义/类型匹配的候选，再用 `maps_search_detail` 核对同一 POI 的坐标和地址 |
| 带门牌的完整地址 | `maps_geo` 后核对城市、门牌和返回层级；街道/区县级结果仍不足以确定门址 |
| 已选定的 POI 或具体入口 | 查询该 POI 详情，保留原选择；不换成同名道路、公园中心或其他入口 |
| 城市/商圈/道路范围、模糊“附近” | 请用户给具体地标、路口、门牌或入口，不替用户任挑一个中心点 |

地标查询即使只返回一条 `level=道路` 的有效坐标，也不能当成地标已经确定。
先排除不匹配城市/类型的同名道路、地铁站、公交站，并按 POI ID 去重：
**唯一合理候选**可说明具体名称、地址和“采用地图标注点”后继续，不声称用户确认了入口；
**仍有多个合理候选**则展示差异并等待选择，不能因为“快点、别问”就取搜索第一条。
坐标缺失、`0,0`、详情失败或与候选身份冲突时保留未定位状态，不借用另一结果的坐标。

进入路由前保存点位记录：用户原话、城市、路线点标识、名称、地址、POI ID（确有返回时）、
坐标及坐标来源、选定依据（唯一匹配/用户选择/精确门址）、入口是否确认。
同一记录贯穿路由、计算证据与地图。坐标或 POI 改变时，废弃并重查以此点为端点的路段；
重算总里程、所有受影响的到离时刻和营业覆盖，重新生成地图。环线首段和末段都要检查。
点位记录只是可核对的输入，不是脚本已经验证语义或入口通行的证明。

## 4. 生成候选路线

**点到点：**起终点已确定后，先查询对应运动方式的 A→B 基线路线，再在实际路线附近找候选补给点。
需要停靠时查询 A→站点→B 的每一段，记录相对基线增加的道路里程。

**环线：**围绕起点寻找合适的公开道路/地点，构造起点→途经点→起点的候选；
途经点也先完成第 3 步，每一段分别查询路网，再相加并调整途经点，最多向用户展示三条有证据的候选。
不能用“起点=终点”的零距离查询代替环线，也不能用直线距离相加凑里程。
闭合不等于不重复：有折返或共享路段时明确说明，不冒充无重复环线。

跑步使用步行路网作为候选，骑行必须用骑行路网，不能换用驾车路线。
用户目标里程不是可以随意突破的硬上限：说明与目标的偏差，超出明确上限的候选
只能展示为不满足要求，不能悄悄放宽。没有合适候选就如实说未找到。
定位、道路访问、几何或路线查询失败，不用模型生成路名/线段补齐。

## 5. 验证补给点和夜间时间

- 用门店名称、完整地址、城市与坐标交叉匹配地图地点和麦当劳门店。
  地图 POI ID 不是麦当劳 `storeCode`；同名不同址不能直接合并。
- 到店休息/取餐的候选查询使用 `beType=1`，骑车不等于得来速 `beType=5`。
- 按每段运动时间和前面所有停留，计算各站预计到达与离开时间。
- 检查**整个停留区间**是否落在该日期的营业窗口内，不只看当前营业状态。
  预约取餐时段不是餐厅营业时间；`24小时` 标记也要确认适用日期、渠道和入店条件。
- 没有可靠营业窗口就标记“到访时段营业情况未知”。开放取餐窗口不等于可以进店休息；
  座位、卫生间、饮水、充电、自行车停放和夜间堂食均不能从品牌或开门状态推断。
- 不把“有麦当劳”推断为路灯充分、有人流或路线安全；照明/封闭信息缺失就明确未知。

需要餐品时才查询该店菜单；有预约时间就按工具定义传入。
本版不进行下单、预约锁单、自动领券或积分操作。

## 6. 用脚本复核数字

读 [计算输入约定](references/route-input.md)，把已查询的完整道路分段和有依据的
日期营业窗口整理为 JSON，存到仓库外临时目录或被忽略的 `.runtime`。
`evidence` 引用当前查询/快照，不编造已查询的证据；保留原始返回供人工核对。
先对照点位记录确认各段起终点坐标一致；不要把旧坐标的路由距离换个名称继续使用。
点位记录另存，不给计算器 JSON 塞入未支持的字段。

将以下路径解析为**本 Skill 所在目录下的文件**，不要假设用户工作目录就是仓库：

```text
python <Skill目录>\scripts\route_metrics.py <临时路线.json>
```

脚本只验证输入、计算里程/时刻和窗口覆盖，**不查询路网、不核实来源、不认证路线安全**。
跑步耗时按配速计算，骑行耗时使用地图骑行结果；实际速度可能变化。
`has_known_conflict=false` 仅表示没有发现已知冲突，未知营业情况依然未知。
脚本报错则纠正数据或停止，不改成心算、静默跳过或套用演示结果。

## 7. 交付路线卡片

每条候选按以下顺序输出：

1. **结论**：推荐候选 / 不满足条件 / 数据不足，以及关键原因。
2. **路线**：模式、形态、起终点采用的具体 POI/门址、入口是否确认、途经点、总道路距离、目标偏差、相对基线的绕行距离（有基线时）。
3. **时间**：出发与结束日期时刻、时区、运动与休息时长，注明估算依据。
4. **补给表**：门店、到达/离开、营业窗口、窗口覆盖状态、是否能进店休息的证据。
5. **地图入口**：仅用工具实际返回或官方已验证格式的链接；单目的地导航不是完整环线导航。
6. **不确定项与来源**：查询时间、数据来源、营业/照明/道路限制未知项；出发前需再确认。

示例触发语：
“今晚九点在上海从某地跑八公里再回来，六分配速，中途想在麦当劳歇十分钟。”
这里“某地”必须向用户确认，不能自行替换成真实地点。

安装包中的 `examples/night-loop.json` 是虚构数据，演示一个跨午夜时
“到店时没关门，但停满十五分钟会超过关门时间”的反例，不可用于导航。
